2. MIGRAÇÃO E CONFIGURAÇÃO

Migrados integralmente Gateway, Pedidos, Estoque, Pagamento e Notificação:
domain, application/ports, application/usecases, adapters/in, adapters/out,
infrastructure e server. O código de negócio foi adaptado, sem reimplementar
fluxos ou alterar tabelas. Os scripts SQL permanecem inalterados.

Cada serviço possui tsconfig.json independente, com:
- strict: true, noEmitOnError: true e skipLibCheck: false;
- target ES2022, module CommonJS, moduleResolution Node;
- rootDir '.', outDir 'dist', declarations e source maps habilitados;
- node_modules e dist excluídos das fontes.

As dependências de execução existentes foram preservadas. Foram adicionados
apenas TypeScript ~5.7.3 e definições @types/node 20, @types/express 4 e,
nos quatro serviços com mensageria, @types/amqplib. Os cinco lockfiles foram
atualizados. Não foram introduzidos ORM, framework de DI, ts-node ou tsx.

Os imports são estáticos TypeScript, incluindo import type nas dependências
que só existem na compilação. CommonJS foi preservado: export = mantém os
require() dos testes .cjs compatíveis com as classes compiladas; módulos com
exports nomeados continuam com exports nomeados. Interfaces não são usadas
como classes-base e não são instanciadas em runtime.

Não há any explícito nas fontes do backend. Entradas já validadas por Estoque,
Pagamento e Notificação usam unknown com guardas de tipo. Resultados MySQL
usam RowDataPacket, ResultSetHeader e tipos concretos de linha, restritos aos
adaptadores. Erros capturados são tratados a partir de unknown, com funções
puras de inspeção; o domínio continua sem dependências externas. Os DTOs REST
e eventos são locais a cada serviço. Não foi criado pacote compartilhado nem
import de domínio de um serviço por outro: preservam-se builds e fronteiras
independentes. Os testes de integração verificam a compatibilidade dos JSONs.

Scripts por serviço:
- build: tsc -p tsconfig.json
- typecheck: tsc -p tsconfig.json --noEmit
- start: node dist/server.js
- dev: tsc -p tsconfig.json --watch
- dev:serve: node --watch dist/server.js

Dockerfiles agora têm duas etapas: npm ci e compilação na etapa build;
na imagem final, npm ci --omit=dev e cópia de dist. A execução é
node dist/server.js, com Node 20. Cada .dockerignore exclui node_modules
e dist para não copiar artefatos do host. Compose, portas e volumes foram
preservados. Não foi removido nenhum volume nem interrompido outro projeto.

4. ARQUITETURA E COMPATIBILIDADE

SOA + Arquitetura Hexagonal preservadas. Domínio não depende de aplicação,
adaptadores, infraestrutura ou bibliotecas; aplicação depende de domínio e
portas. Express, mysql2 e amqplib ficam nos adaptadores/infraestrutura.

A melhoria central é a formalização das abstrações: foram substituídas as
classes-base provisórias e a tipagem implícita por interfaces implementadas
explicitamente e dependências de construtor verificadas pelo compilador.
Não foi necessário corrigir importações de infraestrutura no domínio, pois
essa separação já estava correta. O comentário desatualizado de Pedidos sobre
manter reserva após recusa foi alinhado ao ADR-0004, sem alterar o fluxo.
Não foi introduzida Clean Architecture nem uma camada adicional.

Contratos preservados:
POST /checkout; POST /pedidos; POST /reservas; POST /cobrancas;
GET /notificacoes. Os JSONs e códigos de resposta existentes permanecem.
Exchange loja.eventos/topic; routing keys pagamento.aprovado,
pagamento.recusado e pedido.status.alterado; campos evento, pedidoId,
valor, status, motivo e data conforme o evento. As filas de resultados de
Pedidos e Estoque continuam independentes.

Garantias preservadas:
- Reserva multitem atômica, UPDATE condicional, rollback e locks MySQL.
- Agrupamento de itens e idempotência persistente por pedido.
- Aprovação reduz saldo e reservado; recusa libera apenas reservado.
- Cobrança e outbox na mesma transação, confirmação e republicação de pendências.
- Notificação com chave única e confirmação após processamento.
- Retry atrasado, fila durável de erro e reconexão em Estoque/Notificação/Pagamento.

Pendências anteriores preservadas, fora do escopo da migração:

- Gateway/Pedidos mantêm sua validação e tratamento HTTP originais. Tipos
  TypeScript não substituem validação runtime de JSON não confiável.
- Adaptadores HTTP de Pedidos preservam a leitura dos JSONs existentes;

- Limites de envio externo versus commit e de idempotência de gateway real

- Não foram feitos testes prolongados de carga nem testes com provedores reais.

e checkouts aprovados consomem unidades do seed, como antes. Nenhuma fila
foi purgada. Os contêineres pies-academia de outro projeto não foram afetados.
Portas mantidas: 3000 a 3004, MySQL 3307, AMQP 5672 e painel RabbitMQ 15672.

6. MAPEAMENTO PARA UML DE CLASSES (SEM GERAR DIAGRAMAS)

Classes de domínio:
- Gateway.RequisicaoCheckout: clienteId, itens e simularRecusa normalizados.
- Pedidos.Pedido: itens, total, StatusPedido; criar, pagar e cancelar.
- Estoque.ItemEstoque: saldo/reservado e operações de reserva/baixa/liberação.
- Pagamento.Cobranca: pedidoId, valor e estado da cobrança; aprovar/recusar.
- Notificacao.Notificacao: pedidoId, canal, mensagem e enviadoEm.
ItemReserva, ItemPedido, Aviso e os eventos são tipos de dados/DTOs; não
precisam ser confundidos com entidades que possuem identidade própria.

Para cada serviço, incluir como <<interface>> as portas listadas na seção 3;
incluir os casos de uso e adaptadores concretos correspondentes. Qualificar
os nomes por serviço, porque EventosPublicador e EventosPublicadorRabbit
existem em Pedidos e Pagamento e possuem contratos diferentes.

Relações a representar:
- Realização de interface: Gateway.PedidosApiHttp implementa Gateway.PedidosApi;
  Pedidos.PedidoRepositorioMysql implementa PedidoRepositorio; Estoque.Estoque-
  RepositorioMysql implementa EstoqueRepositorio; Pagamento.GatewayPagamentoMock
  implementa GatewayPagamento; Notificacao.CanalEnvioMock implementa CanalEnvio;
  e as demais realizações explicitadas por implements nas fontes.
- Generalização entre interfaces: Pagamento.CobrancaRepositorio estende
  Pagamento.PersistenciaOutbox. Não é herança entre classes concretas.
- Dependência/associação injetada: cada caso de uso mantém referências privadas
  readonly às portas enumeradas na seção 3. Desenhar a relação com a interface,
  sem apontar o caso de uso diretamente ao adaptador concreto.
- Criação/composição de objetos: infrastructure/container.ts é o composition
  root, cria adaptadores e casos de uso. É uma função, não uma classe de domínio.
  Usar nota/pacote ou dependência de criação; não inventar uma classe Container.
- Domínio: Pedido contém sua coleção de ItemPedido; os demais casos de uso
  criam/usam as entidades e DTOs locais. A transação/lock pertence ao adaptador
  MySQL, não à entidade pura.
- Adaptadores de entrada: rotas e consumidores são funções que dependem de
  portas de entrada. Podem ser apresentados como operações de módulo/notas;
  não inventar classes para funções que não existem no código.

7. COMANDOS REPRODUZÍVEIS

Pré-requisitos: Node 20, npm e Docker Compose.
Na raiz do repositório:

  npm run install:services
  npm run build
  npm run typecheck
  npm test

npm test executa build, verificação dos contratos de tipos e os 39 testes
unitários/arquiteturais. Para executar cada etapa isolada:

  npm run test:types
  npm run test:unit

Por serviço (substituir estoque pelo serviço desejado):

  npm --prefix src/estoque ci
  npm --prefix src/estoque run build
  npm --prefix src/estoque run typecheck
  MYSQL_HOST=127.0.0.1 MYSQL_PORT=3307 npm --prefix src/estoque start

Os demais valores vêm de infrastructure/config.ts, incluindo credenciais,
RabbitMQ e URLs HTTP. Para desenvolvimento, primeiro fazer build; em um
terminal executar npm --prefix src/estoque run dev e em outro executar
npm --prefix src/estoque run dev:serve. Não executar a versão local e Docker
na mesma porta simultaneamente.

Aplicação completa em Docker:

  docker compose config --quiet
  docker compose up -d --build
  docker compose ps

Integração (fazer npm run build no host antes de montar o repositório):

  docker compose run --rm --no-deps -v "$PWD:/projeto:ro" pagamento node /projeto/tests/integracao.cjs

Recuperação real, somente no ambiente de demonstração (para o broker do projeto):

  docker cp tests/recuperacao.cjs loja-pagamento:/tmp/recuperacao.cjs
  docker compose exec -T pagamento node /tmp/recuperacao.cjs preparar
  docker compose restart estoque pagamento notificacao
  # aguardar os servidores escutarem
  docker compose exec -T pagamento node /tmp/recuperacao.cjs reinicio
  docker compose stop rabbitmq
  docker compose exec -T pagamento node /tmp/recuperacao.cjs offline
  docker compose start rabbitmq
  # aguardar RabbitMQ saudável e reconexão dos consumidores
  docker compose exec -T pagamento node /tmp/recuperacao.cjs recuperado
